# AI and Tool-Use Note

**Tools.** Claude Code (Opus 5) as the primary development environment, for code,
documentation drafting and API probing. Google Gemini `gemini-3.5-flash-lite` inside the
product itself, for two of the five pipeline stages. No other AI tooling.

**Where AI did the work.** Scaffolding, the zod contracts, the Next.js screens, the eval
harness plumbing, and first drafts of every document here were AI-generated and then edited.
The synthetic registry and the 60 case reports are machine-generated by committed scripts.

**Where it did not.** The problem selection, the decision that warranty determination must
be deterministic, the routing table, the two-denominator definition of leakage, and the
choice of validation primary metric are judgment calls made by me. The warranty policy was
written first, by hand, precisely so that neither the rules engine nor the eval labels could
be reverse-engineered from model behaviour.

**Material prompts.** Three prompts are load-bearing and all are versioned and committed:
`extract/v1` (`src/agent/extract.ts`), `draft/v1` (`src/agent/draft.ts`), and `realize/v1`
(`src/data/generate-cases.ts`). Two constraints in them carry most of the weight — EXTRACT is
forbidden from naming an asset and may only emit descriptors, and the realizer is never shown
any label field. A fourth, `decide-llm/v1`, exists only to be beaten in the ablation.

**How outputs were verified.**

- **Model behaviour was measured, not assumed.** The model list advertises 41 models; most
  return `404 … no longer available to new users` on a new free-tier key. The pinned model is
  one I actually called. Default thinking spent 521 thought tokens on a 16-token prompt, so
  `thinkingLevel` is set explicitly.
- **Every LLM output is checked by deterministic code.** EXTRACT is cross-checked against a
  keyword lexicon and scored for agreement; a severity without a verbatim evidence span is
  dropped. DRAFT prose is checked token by token against the structured payload.
- **33 unit tests** assert the rules engine against the policy document, including an
  exhaustive sweep proving no covered asset can reach a paid-vendor route.
- **The evaluation reproduces offline** from committed fixtures with no API key.

**Limitations I am aware of.** Decision ground truth is computed by the same rules the
pipeline applies, so E3 measures whether the pipeline feeds the rules correctly — not whether
the rules are right; those are tested separately. The case set is n=60 and deliberately
skewed toward the warranty boundary, so absolute rates are not production estimates. The
reports are LLM-written and messier than a template but not real intake.

**Mistakes worth recording.** The pre-commit secret scanner passed its own first test against
a 38-character dummy key because the pattern demanded exactly 35 suffix characters; a scanner
that only catches perfectly-formed keys is worse than none, because it gets trusted. And the
rate limiter was built for a per-day quota when the binding free-tier constraint is per
minute — found by exhausting quota at call 49 with token usage nowhere near any limit.
